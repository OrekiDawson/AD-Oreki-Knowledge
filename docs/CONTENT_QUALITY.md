# AD-Oreki 知识库内容质量标准

> GitHub 的原始源码、Commit、PR、Run 与设备实证才是事实依据。Quartz 站点只是衍生展示层。

## 什么才算一篇合格条目

正式专题文章应当确实回答读者的问题，而不是仅罗列规则或复制开发日志。根据主题提供：

1. **一句话结论与状态**：已验证 / 进行中 / FAIL / BLOCKED / 待确认 / 已推翻，明确适用版本与最后核实日期。
2. **问题、影响范围和原理**：如协程 ABI，说明触发条件、调用边界、关键描述符、根因和解决机制；如存档，说明写读路径和跨构建区别。
3. **可操作资料**：相关源码文件、实际路径、复现条件、必要命令（不含密钥或私有路径）、最小验证步骤及已知限制。
4. **直接证据链接**：优先指向固定 Commit 的具体文件/行，至少提供原始 PR、报告或 GitHub Actions Run 的可点击 URL。不能只写 `PR #88` 或一个无链接 SHA。
5. **结论历史**：旧判断、否定它的证据、当前有效结论，不覆盖或删除历史；明确「已测」「推断」「尚未测」。
6. **关联与版本边界**：关联 Wiki 条目和 Android/Web 差异；不要用一次本地 AVD PASS 宣称全部发行门禁已通过。

不同页面不必死板套模板，但不能用空泛口号、无证据的 PASS、无目的的表格填篇幅。**不以页数、字数、AI Token 数或知识图谱节点数评定质量。**

## 关键状态页的更新纪律

- Android 和 Web 上游事实变更（特别是 P0、长跑目标、发布、存档、跨端差异）后，知识库状态页应同步实际结果，或标记「截至 SHA/日期，可能过期」，不能继续陈述已失效的「运行中」。
- 每条重要 PASS、FAIL、BLOCKED 都必须能够从 Wiki 直接点到原始证据。
- 无法验证的新声明写 **NOT VERIFIED**，不能自行改成 PASS。
- 对外正式发布前单独核对 Android/Web 当前 main 与关键 Issue/报告；CI 构建成功不等于事实审核完成。

## 未审核 AI 草稿

- `content/ai-drafts/` 允许作为 GitHub 中待审证据，不允许出现在正式 Quartz 页面、站点搜索索引、RSS 或可见的 AI 问答检索中。
- AI 建议必须人工核对来源，合格后改写或合并到**独立正式专题**，绝不直接把草稿状态从「待审」批量改成「已验证」。
- 如无有效证据宁可不发布该条目，保留为待办。

## 分批改造顺序

1. **P0 事实止血**：修正当前状态中的已知错误（例如 R113-01 180 分钟长跑 FAIL）、隐藏未审核 AI 草稿，完善最基本的证据链。
2. **P1 专题深挖**：优先 Kotlin/DEX 混合 ABI、AGP/Signature/存档、挑战真实结算与阶段门禁、180 分钟长跑失败分析、双端等价，每次处理少量条目并逐条核验。
3. **P2 可用性**：真实来源目录、索引、图谱关联、移动端、导航与历史归档。

本标准不允许借知识库建设重置 R113-01 编号、修改游戏基线、跳过保护门禁、擅自发布 APK 或覆盖 `docs/FACTS.md`。
